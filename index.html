01FOUNDATION

1. 하네스·루프·그래프 엔지니어링은 무엇이 다른가

세 용어는 서로를 대체하는 유행어가 아니라, 에이전트 시스템의 서로 다른 설계 층을 가리킨다.

최근 AI 에이전트 분야에서는 프롬프트 엔지니어링과 컨텍스트 엔지니어링을 넘어 하네스 엔지니어링, 루프 엔지니어링, 그래프 엔지니어링이라는 표현이 연이어 등장했다. 세 개념은 경쟁 관계가 아니다. 하네스는 에이전트가 일하는 환경, 루프는 시간이 흐르며 일을 지속하는 방식, 그래프는 여러 실행 주체와 상태 사이의 관계를 설계한다.

ENVIRONMENT

하네스 엔지니어링

모델이 안정적으로 일할 수 있도록 컨텍스트, 도구, 권한, 메모리, 샌드박스, 검증과 관측 환경을 설계한다.

TIME

루프 엔지니어링

사람이 매번 다음 프롬프트를 입력하는 대신 목표·검증·중지 조건을 따라 실행이 반복되게 한다.

RELATIONSHIP

그래프 엔지니어링

여러 에이전트, 루프, 결정적 코드와 사람 승인을 명시적 노드·경로·공유 상태로 조율한다.

모델은 하네스 안에서 행동하고, 루프는 행동을 반복하며, 그래프는 반복 사이의 관계를 구조화한다.

1.1 하네스 엔지니어링: 모델이 일할 세계를 설계한다

하네스는 단순한 프롬프트 래퍼가 아니다. 파일 시스템, 터미널, 검색, 브라우저, 외부 API, 승인 체계, 컨텍스트 압축, 작업 복구, 테스트 실행, 비용 제한까지 모델과 현실 세계 사이의 인터페이스 전체를 포함한다.

model intelligence × harness quality × task verifiability
= dependable agent performance

1.2 루프 엔지니어링: 시간과 반복을 설계한다

루프는 트리거에서 시작해 상태를 읽고, 다음 작업을 선택하고, 에이전트를 실행하고, 결과를 검증한 뒤 상태를 기록한다. 성공·대기·재시도·에스컬레이션 가운데 하나를 선택하며 필요할 때 다시 돈다.

  1. 트리거 — 언제 시작하는가
  2. 목표 — 무엇을 달성해야 하는가
  3. 검증 — 달성 여부를 어떻게 확인하는가
  4. 중지 — 성공·실패·차단·예산 소진 중 언제 멈추는가
  5. 외부 상태 — 다음 실행이 이전 진행을 어떻게 아는가

1.3 그래프 엔지니어링: 관계와 책임 경계를 설계한다

그래프는 순서가 중요하거나, 병렬 작업을 합쳐야 하거나, 권한과 검증 방식이 다른 작업자를 분리해야 할 때 의미가 있다. 모든 노드가 LLM일 필요는 없다. 정규식, 스키마 검사, 권한 판정은 코드가 하고 모호한 판단과 새로운 전략만 모델이 맡는 구성이 더 강하다.

책임 조율

2.1 프롬프트 엔지니어링: 한 번의 추론을 정렬한다

초기에는 역할, 예시, 출력 형식, 사고 단계처럼 한 번의 모델 호출 품질을 높이는 방법이 중심이었다. 여전히 중요하지만, 파일과 도구를 쓰며 수십 분 이상 작업하는 에이전트의 실패는 프롬프트만으로 설명되지 않는다.

2.2 컨텍스트 엔지니어링: 지금 필요한 정보를 보여준다

긴 지침을 모두 밀어 넣는 대신 저장소의 짧은 지도, 작업별 문서, 검색 가능한 기록, 실행 계획을 조합한다. 컨텍스트 엔지니어링은 하네스의 핵심 구성요소지만 전부는 아니다. 정보를 잘 보여줘도 도구, 권한, 상태와 검증이 부실하면 에이전트는 실패한다.

2.3 하네스 엔지니어링: 모델이 성공할 수 있는 환경을 만든다

OpenAI의 Codex 기반 제품 개발 사례는 사람이 코드를 직접 쓰기보다, 에이전트가 읽을 수 있는 저장소와 검증 가능한 요구사항, 구조적 테스트와 커스텀 린터를 만드는 쪽으로 엔지니어의 일이 이동함을 보여줬다.

모델에게 더 열심히 하라고 요구하기보다, 모델이 성공할 수 있는 환경을 만들어야 한다.

2.4 루프 엔지니어링: 사람이 반복하던 ‘다음’을 제거한다

코딩 에이전트가 장시간 작업할 수 있게 되자, 사람이 계속 “계속해”, “테스트해”, “다시 확인해”라고 입력하는 일이 병목이 됐다. 루프는 목표·증거·예산·중지 조건을 외부 상태와 결합해 이 반복을 시스템으로 옮긴다.

2.5 그래프 엔지니어링: 프로덕션 책임을 명시한다

탐색이 끝나고 반복되는 절차와 경계가 안정되면, 작업 순서·병렬성·승인·복구를 그래프로 승격할 수 있다. 그래프는 창의성을 제거하는 족쇄가 아니라 창의적 판단을 허용할 안전한 경계다.

03SURVEY

3. 파편화된 담론을 하나의 지도에 놓기

주요 스피커와 팀은 서로 다른 이름을 쓰지만, 공통적으로 모델 밖의 환경·반복·상태를 엔지니어링 대상으로 끌어낸다.

하네스·루프·그래프라는 말은 하나의 표준 문서에서 동시에 정의된 것이 아니다. 서로 다른 현장에서 관찰된 병목에 이름을 붙이며 합류한 개념이다. 따라서 누가 어떤 단어를 먼저 썼는지보다, 각 관점이 해결하려는 실패가 무엇인지 읽어야 한다.

3.1 공통된 전환

모든 관점은 모델의 답변 품질만 보던 시선에서 벗어나, 모델이 읽는 정보와 사용할 수 있는 도구, 실패 후 돌아올 상태, 완료를 판정하는 증거, 사람이 개입하는 경계를 함께 설계한다.

3.2 용어보다 중요한 질문

  • 에이전트가 실패한 원인은 모델, 도구, 컨텍스트, 권한, 검증 중 어디에 있는가?
  • 같은 실패가 반복된다면 프롬프트를 고칠 것인가, 환경을 바꿀 것인가, 결정적 코드로 막을 것인가?
  • 반복과 그래프가 실제 책임 경계를 해결하는가, 단지 역할 이름만 늘리는가?
04MECHANISM

4. 에이전트 내부 루프와 시스템 외부 루프

에이전트가 한 번의 세션에서 계획–행동–관찰을 반복하는 것과, 시스템이 세션을 다시 시작하는 것은 다른 설계 문제다.

INNER LOOP

에이전트 런타임 내부

모델이 도구를 고르고 결과를 관찰하며 다음 행동을 정한다. 컨텍스트 윈도, 도구 오류, 압축과 완료 판단에 영향을 받는다.

think → act → observe → revise
OUTER LOOP

런타임 밖 제어 시스템

목표, 예산, 체크포인트, 검증 결과를 읽어 새 실행을 시작하거나 대기·중지·사람 호출을 결정한다.

trigger → run → verify → persist → decide

강한 모델과 좋은 내부 루프는 한 세션의 생산성을 높인다. 그러나 네트워크 응답을 기다리거나 다음 날 다시 시작해야 하는 작업, 여러 저장소나 이슈 상태를 넘나드는 작업은 외부 루프가 필요하다.

4.1 외부 루프가 필요한 신호

  • 에이전트가 한 번의 응답 후 너무 일찍 멈춘다.
  • CI, 리뷰, 외부 API처럼 늦게 도착하는 신호를 기다려야 한다.
  • 다음 실행이 이전 세션의 진행 상황을 알아야 한다.
  • 실패 시 같은 세션을 계속 늘리기보다 새 컨텍스트로 복구하는 편이 낫다.

4.2 루프가 해결하지 못하는 것

목표가 모호하고 성공 조건이 주관적이라면 반복은 품질을 보장하지 않는다. “계속 개선해”라는 무한 루프는 목표 미정 상태를 자동화할 뿐이다. 먼저 완료 계약을 만들고, 그 계약을 기계적으로 확인할 수 있는 증거를 마련해야 한다.

05MODEL × RUNTIME

5. 모델 지능과 하네스는 서로를 대체하지 않는다

강한 모델은 단순한 하네스에서도 많은 일을 해내지만, 운영 경계와 검증까지 스스로 만들어 주지는 않는다.

약한 하네스강한 하네스강한 모델빠르지만 권한·복구·검증이 불안정
높은 잠재력, 높은 변동성복잡한 목표를 적은 규칙으로 수행
가장 높은 일반 생산성중간 모델도구 혼동과 장기 목표 이탈
작은 작업만 적합도구 축소·기계 검증으로 안정화
비용 효율적 자동화

모델이 발전하면 하네스가 사라지는 것이 아니라 역할이 바뀐다. 약한 모델을 보정하기 위한 장황한 규칙은 줄고, 권한·도구 인터페이스·외부 상태·관측·검증 같은 안정된 운영 경계가 더 중요해진다.

5.1 모델별 프로필이 필요한 이유

모델마다 병렬 도구 호출, 질문 성향, 컨텍스트 압축 내성, 도구 오류 후 복구, 완료를 선언하는 시점이 다르다. 같은 30개 도구와 같은 턴 예산을 모든 모델에 적용하면 공통 인터페이스는 얻지만 최적 성능은 잃는다.

  • 강한 모델: 도구와 규칙을 덜 강제하고 복잡한 판단을 직접 맡긴다.
  • 중간·로컬 모델: 업무별 도구를 줄이고 목표를 짧게 하며 외부 검증을 강화한다.
  • 고비용 모델: 설계, 난해한 오류, 최종 리뷰와 목표 재설계에 선택적으로 사용한다.
자율성은 모델이 얼마나 똑똑한가보다, 결과가 얼마나 검증 가능한가에 더 직접적으로 제한된다.
06HARNESS PROFILE

6. Codex: 모델과 하네스의 강한 통합

소프트웨어 작업을 위한 도구·샌드박스·계획·검증 흐름을 하나의 제품 경험으로 결합한다.

Codex의 강점은 모델 성능만이 아니라 저장소 탐색, 파일 수정, 명령 실행, 승인, 작업 계획, 결과 검증이 촘촘하게 결합된 실행 환경에 있다. 사용자는 목표를 주고 에이전트는 같은 작업공간에서 조사–수정–테스트를 이어간다.

강점
  • 코딩 모델과 런타임의 공동 최적화
  • 작업공간 중심의 높은 실행 완결성
  • 샌드박스·승인·도구 호출의 일관된 경험
  • 계획, 수정, 빌드, 검증까지 한 흐름
주의점
  • 제품이 제공하는 실행 모델과 생태계에 상대적으로 결합
  • 지속형 개인 메모리·메시징 자동화가 핵심 목적은 아님
  • 여러 외부 시스템을 장기간 조율하려면 별도 상태 계층 필요

적합한 작업: 저장소 단위 기능 구현, 버그 수정, 리팩터링, 테스트·빌드 오류 해결, 코드 리뷰와 배포 가능한 웹 산출물 제작.

07HARNESS PROFILE

7. Claude Code: 강한 추론과 터미널 조합성

터미널을 중심으로 사용자가 훅·명령·서브에이전트와 외부 자동화를 직접 조합하기 좋다.

Claude Code는 강한 장문 이해와 추론, 터미널 친화성, 프로젝트 지침과 훅을 이용한 조합성이 돋보인다. 사용자가 셸 스크립트, 워크트리, CI, 이슈 트래커와 연결해 자신만의 루프를 만들기 쉽다.

강점
  • 복잡한 코드베이스와 장문 지시 이해
  • 터미널·Unix 도구와 높은 조합성
  • 훅과 에이전트 팀을 이용한 확장
  • 사용자 주도 루프 설계의 자유도
주의점

  • 팀·루프가 늘면 컨텍스트 복제와 합성 비용 증가
  • 권한·상태·완료 조건을 사용자가 명확히 설계해야 함

적합한 작업: 복잡한 저장소 조사, 설계와 구현을 넘나드는 장기 코딩, 터미널 중심 자동화, 사용자가 직접 조율하는 병렬 작업.

08HARNESS PROFILE

8. Hermes: 지속 기억과 모델 독립형 개인 에이전트

코딩 도구라기보다 기억·스킬·메시징·자동화를 결합해 장기 운영하는 개방형 에이전트 환경에 가깝다.

Hermes는 특정 모델이나 코딩 화면에 강하게 묶이지 않고 다양한 모델, 도구, 스킬, 메시징 채널과 지속 기억을 조합한다. 항상 켜져 있는 개인·업무 에이전트, 로컬 모델과 클라우드 모델의 혼합 운영, 예약·이벤트 기반 작업에 적합하다.

강점
  • 모델 독립성과 로컬·클라우드 혼합
  • 지속 메모리, 스킬, 메시징 채널
  • 프로필별 도구와 모델 구성
  • 개방형 자동화와 장기 운영
주의점
  • 도구가 많을수록 중간 모델의 선택 정확도 하락
  • 메모리·스킬의 중복과 부패 관리 필요
  • 프라이버시 경계와 채널별 권한 분리 필요
  • 구성 복잡성과 모델 편차를 운영자가 감당

개인·업무·코딩·공용 채널 프로필을 분리하고 각 프로필의 메모리, 도구, 권한, 모델, 기록 보존 정책을 다르게 두는 편이 안전하다. 고난도 설계·리뷰는 강한 모델, 검색·정리·반복 수정은 로컬 모델에 맡기는 포트폴리오가 효과적이다.

11PRACTICE

11. 다양한 사용자에게 권장하는 방향

대부분의 개인 사용자는 강한 단일 에이전트와 검증 가능한 저장소, 작은 루프에서 가장 높은 비용 대비 효과를 얻는다.

11.1 일반 코딩 에이전트 사용자

강한 에이전트 하나로 시작하고 프로젝트 지침을 짧게 작성한다. 테스트·린트·빌드 명령을 알려주고, 작업 전 계획과 작업 후 검증을 요구하며, 반복되는 절차만 스킬로 저장한다. 가장 큰 효과는 멀티에이전트가 아니라 검증 가능한 저장소에서 나온다.

11.2 파워 유저와 1인 개발자

이슈 조사, 테스트 실패 수정, 의존성 업데이트, 문서 정리처럼 작은 루프를 도입한다. 자동 병합보다 검토 가능한 PR 생성을 기본 종료 상태로 둔다.

발견 → 변경 → 테스트 → 독립 리뷰 → PR 생성 → 사람 승인

11.3 개발 팀과 기술 리더

저장소 지식, 실행 가능한 요구사항, 빠르고 결정적인 테스트, 아키텍처 규칙의 린터화, 관측 가능한 실행, 격리 작업공간, PR·이슈 기반 오케스트레이션을 우선한다. 에이전트 수가 늘수록 사람의 리뷰 대역폭을 보호해야 한다.

11.4 로컬·오픈 모델 사용자

프로필별 도구 수를 줄이고 업무별 스킬, 작은 작업 단위, 파일 기반 계획과 상태, 짧은 목표 루프와 기계 검증을 사용한다. 로컬 모델은 검색·정리·로그 분석·단순 구현, 강한 클라우드 모델은 아키텍처·난해한 오류·최종 리뷰에 배치한다.

11.5 Hermes 같은 지속형 개인 에이전트 사용자

개인·업무·코딩·공용 채널 프로필의 메모리, 도구, 권한, 메시징 채널, 스킬, 모델, 보존 정책을 분리한다. 지속 기억은 많이 저장하는 것보다 무엇을 저장하지 않을지가 중요하다.

11.6 에이전트 플랫폼 개발자

1. Agent Runtime — 모델·도구·컨텍스트·권한·세션
2. Loop Controller — 목표·예산·검증·대기·재시도
3. Workflow Orchestrator — 의존성·병렬·승인·복구

세 레이어를 분리하면 모델이나 하네스를 바꿔도 업무 상태를 유지하고, 작은 루프에서 시작해 필요한 경계만 그래프로 확장할 수 있다.

12OPERATING RULES

12. 실무 설계 원칙

좋은 시스템은 에이전트 수가 아니라 완료 계약, 증거, 상태, 실패 경계를 올바르게 배치한다.

01

가장 작은 구조에서 시작한다

함수 → 모델 호출 → 단일 에이전트 → 루프 → 그래프 순으로, 아래 단계가 실제로 부족할 때만 올라간다.

02

목표보다 완료 계약을 작성한다

결과, 검증, 제약, 범위, 중지 조건을 명시한다. “인증을 개선해”보다 테스트와 비변경 범위를 적은 계약이 강하다.

03

작성자와 검증자를 분리한다

작성 에이전트·모델·프롬프트와 검증을 분리하되, 모델 리뷰보다 테스트·타입 검사·실행 결과를 우선한다.

04

완료는 발언이 아니라 상태 전이다

IMPLEMENTED --test evidence--> VERIFIED
VERIFIED --human approval--> READY_TO_MERGE
05

상태를 대화 밖에 둔다

Git 계획 파일, JSON 상태, 이슈, 체크포인트 DB, 테스트 리포트, 구조화 로그에 진행을 남긴다.

06

에이전트가 아닌 실패 경계를 분리한다

권한·컨텍스트·모델 비용·실패 영향·검증·작업공간 수명 주기가 다를 때 분리한다.

07

결정적 코드와 모델 판단을 혼합한다

정규식·스키마·권한은 코드, 모호한 의도·새 전략·코드 작성은 모델, 고위험 전이는 사람이나 정책이 맡는다.

08

루프에는 예산이 있어야 한다

최대 턴·시간·토큰·비용·동시 에이전트·재시도·변경 파일을 제한한다. 예산 소진은 정상 종료 상태다.

09

모델 업그레이드 시 하네스를 다시 단순화한다

낡은 계획 강제, 프롬프트 트릭, 불필요한 서브에이전트, 도구 설명과 압축 임계값을 다시 검토한다.

13FAILURE MODES

13. 자주 발생하는 안티패턴

복잡성을 추가하는 것은 쉽다. 그 복잡성이 실제 실패를 제거하는지 증명하는 일이 어렵다.

거대한 지침 파일

컨텍스트 낭비, 우선순위 소실, 낡고 상충하는 규칙. 짧은 지도와 구조화된 세부 문서로 나눈다.

검증 없는 무한 루프

while true: agent("계속 개선해")는 완료가 없어 비용과 불필요한 변경만 늘린다.

자기 리뷰만 반복

같은 에이전트의 재검토는 유용하지만 독립 테스트와 외부 증거를 대체하지 못한다.

모든 문제의 멀티에이전트화

권한·도구·검증 차이가 없다면 컨텍스트 복제와 합성 비용만 늘어난 역할극이 된다.

그래프를 너무 일찍 고정

사람과 단일 에이전트로 탐색하고 반복을 관찰한 뒤 안정된 경계만 그래프로 승격한다.

모델 차이를 무시한 공통 하네스

병렬 호출, 질문 성향, 압축 내성, 복구 능력에 맞는 모델별 프로필을 허용한다.

개선 없는 관측

로그 수집이 아니라 실패 위치·책임·반복률·변경 효과·비용 대비 품질을 답할 수 있어야 한다.

14MATURITY 0—6

14. 권장 성숙도 로드맵

모든 단계를 거칠 필요는 없다. 대부분의 개인 사용자에게는 2~3단계가 가장 높은 비용 대비 효과를 제공한다.

0

보조 도구

사람이 수행, 모델은 설명과 초안. 모델의 장단점을 파악한다.

1

단일 에이전트

탐색·수정·명령 실행, 매번 사람 검토. 저장소의 에이전트 적합성을 높인다.

2

관리된 하네스

지침·문서·샌드박스·테스트·권한·관측. 같은 작업을 안정적으로 성공한다.

3

검증 가능한 루프

지속 목표·외부 상태·예산·종료 상태. 사람이 입력하던 “다음”을 제거한다.

4

제한된 그래프

명확한 노드·결정적 분기·사람 승인·복구 경로. 순서와 책임을 보장한다.

5

에이전트 포트폴리오

업무별 모델·하네스·병렬 작업·중앙 상태. 비용·속도·품질을 최적화한다.

6

학습하는 시스템

실패 클러스터링·개선 제안·회귀 평가·승인 후 적용. 경험을 시스템 성능으로 누적한다.

15OUTLOOK

15. 하네스는 기반, 루프는 자동화 단위, 그래프는 운영 경계

가장 좋은 시스템은 완전 자율이 아니라 선택적 자율이다.

15.1 하네스 엔지니어링은 기본 인프라가 된다

모델이 좋아져도 파일, 데이터, 권한, 도구, 네트워크, 메모리, 안전 경계, 검증, 사람과 조직은 남는다. 모델의 부족함을 메우는 임시 규칙은 줄고 안정된 인터페이스와 운영 경계는 더 중요해진다.

15.2 루프 엔지니어링은 자동화의 실질적 단위가 된다

사용자는 프롬프트 템플릿보다 언제 시작하고, 무엇을 목표로 하며, 어떤 증거와 범위·비용·중지 조건을 갖는지 정의한 작업 계약을 더 많이 만들게 된다. 프롬프트는 루프 내부 구성요소로 내려간다.

15.3 그래프 엔지니어링은 프로덕션에서 중요해진다

기업과 고위험 업무의 감사 가능한 상태, 책임·권한 격리, 승인, 장애 복구, 장기 실행, 비용·동시성 관리, 여러 시스템 통합을 다룬다.

15.4 선택적 자율의 경계

명확한 규칙   → 코드가 결정
모호한 문제   → 모델이 판단
고위험 전이   → 사람이 승인
성공 여부     → 증거가 결정

16. 더 많은 에이전트가 아니라 더 나은 경계

추상화가 높아질수록 사람의 책임은 줄지 않는다. 올바른 결과가 생성·검증·승인되는 시스템을 만드는 책임으로 바뀐다.

하네스, 루프, 그래프 엔지니어링의 발전은 더 멋진 용어로의 이동이 아니다. 좋은 답을 받는 단계에서 에이전트가 일을 하고, 계속 일하고, 여러 시스템과 함께 일하며, 경험을 통해 개선되는 단계로 중심이 이동하는 과정이다.

Codex는 모델과 하네스를 강하게 통합해 소프트웨어 개발의 높은 생산성을 추구한다. Claude Code는 강한 추론과 터미널 조합성을 기반으로 사용자가 직접 루프와 에이전트 팀을 구성하기 좋다. Hermes는 모델 독립성, 지속 기억, 스킬, 메시징과 자동화를 결합해 장기 운영 가능한 개방형 에이전트 환경을 제공한다.

절대적으로 우수한 에이전트를 찾기보다 다음을 묻는다. 모델이 이 작업을 이해하는가? 하네스가 성공할 환경을 제공하는가? 목표는 검증 가능한가? 반복이 실제로 필요한가? 그래프가 해결할 책임 경계가 있는가? 실패 시 안전하게 멈추고 복구할 수 있는가?

강한 단일 에이전트와 단순한 하네스에서 시작하고, 반복이 확인되면 루프를 추가하며, 책임·권한·실패 경계가 실제로 분리될 때만 그래프로 확장하라.
