에이전트 엔지니어링의 다음 단계
하네스 엔지니어링에서 루프 엔지니어링, 그래프 엔지니어링으로
부제
모델 지능과 에이전트 런타임의 관계, Codex·Claude Code·Hermes의 차이, 그리고 다양한 에이전트 사용자를 위한 실전 방향성

---
문서 요약
최근 AI 에이전트 분야에서는 프롬프트 엔지니어링과 컨텍스트 엔지니어링을 넘어 다음과 같은 용어가 연이어 등장했다.
• 하네스 엔지니어링: 모델이 안정적으로 일할 수 있는 환경을 설계한다.
• 루프 엔지니어링: 사람이 매번 다음 프롬프트를 입력하는 대신, 목표를 향해 반복하는 시스템을 설계한다.
• 그래프 엔지니어링: 여러 에이전트·루프·결정적 절차를 명시적 상태와 경로로 조율한다.
이들을 단순한 유행어의 교체로 이해하면 오해가 생긴다. 실제 구조는 다음과 같은 중첩 관계에 가깝다.
```
프로젝트·업무 그래프
  ├─ 작업 A의 에이전트 루프
  │    └─ Codex·Claude Code·Hermes 등의 하네스
  │          └─ 기반 모델
  │
  ├─ 작업 B의 결정적 프로그램
  ├─ 사람의 승인 단계
  └─ 검증·복구·재시도 경로

즉,
모델은 하네스 안에서 행동하고, 루프는 그 행동을 시간축에서 반복하며, 그래프는 여러 행동과 루프의 관계를 구조화한다.
이 문서의 핵심 결론은 다음과 같다.
1. 세 개념은 대체 관계가 아니라 제어 범위가 확장되는 과정이다.
2. 더 똑똑한 모델이 항상 더 복잡한 하네스를 요구하는 것은 아니다. 오히려 모델이 강해질수록 과도한 규칙과 분기가 성능을 방해할 수 있다.
3. 반대로 중소형·로컬 모델은 명시적 작업 분해, 제한된 도구, 기계적 검증의 도움을 더 많이 받는다.
4. 단일 에이전트가 해결할 수 있는 문제에 그래프를 도입하면 대개 오버엔지니어링이 된다.
5. 그래프는 에이전트 수가 많아서 필요한 것이 아니라, 책임·권한·상태·실패 경계가 달라질 때 필요하다.
6. Codex와 Claude Code는 모델과 하네스가 긴밀하게 공동 설계된 제품이고, Hermes는 여러 모델을 교체하며 사용할 수 있는 개방형 범용 하네스라는 차이가 있다.
7. 에이전트 시스템의 최종 품질은 모델 벤치마크 점수보다 다음 식에 더 가깝다.
```
실제 성과
= 모델 지능
× 하네스 적합성
× 컨텍스트 품질
× 검증 가능성
× 업무 구조의 명확성
× 운영 신뢰성

어느 한 항이 거의 0이면 전체 시스템도 실패한다.

1. 왜 갑자기 새로운 ‘엔지니어링’ 용어가 계속 등장하는가
초기 생성형 AI 사용에서는 한 번의 응답을 잘 받는 것이 중요했다.
```
사람 → 좋은 프롬프트 → 모델 → 좋은 답변

하지만 코딩 에이전트와 범용 작업 에이전트는 한 번의 답변이 아니라 다음과 같은 긴 작업을 수행한다.
```
요구사항 이해
→ 파일 탐색
→ 계획 수립
→ 코드 수정
→ 명령 실행
→ 오류 관찰
→ 재수정
→ 테스트
→ 리뷰
→ 배포 또는 보고

이때 실패 원인은 프롬프트 한 줄에만 있지 않다.
• 필요한 문서를 찾지 못했다.
• 잘못된 도구를 선택했다.
• 컨텍스트가 너무 길어 핵심 제약을 잊었다.
• 테스트를 실행하지 않았다.
• 실패한 명령을 성공한 것으로 오해했다.
• 아직 작업이 남았는데 완료했다고 판단했다.
• 여러 에이전트가 같은 파일을 동시에 수정했다.
• 재시작 후 이전 진행 상태를 잃었다.
• 모델은 올바르게 판단했지만 권한이나 샌드박스가 작업을 막았다.
• 검증 모델이 작성 모델의 결론을 그대로 받아들였다.
따라서 최적화 대상이 다음처럼 확대됐다.
```
프롬프트
→ 컨텍스트
→ 모델을 둘러싼 실행 환경
→ 반복 수행 구조
→ 여러 작업과 에이전트의 전체 구조

이 변화가 각각 프롬프트, 컨텍스트, 하네스, 루프, 그래프 엔지니어링이라는 이름으로 표현되고 있다.
다만 루프 엔지니어링과 그래프 엔지니어링은 아직 확립된 학술 표준이라기보다 실무자들이 새로운 작업 방식을 설명하기 위해 사용하는 신생 용어다. 특히 LangChain의 Harrison Chase와 Sydney Runkle도 그래프 엔지니어링을 완전히 새로운 발명이라기보다, 기존 상태 머신과 에이전트 그래프 설계에 붙은 최신 명칭으로 평가한다.

---
2. 세 개념을 가장 간단하게 구분하는 방법
2.1 하네스 엔지니어링: 공간과 환경을 설계한다
하네스는 모델을 실제로 행동 가능한 에이전트로 만드는 실행 환경이다.
```
하네스 =
  시스템 지침
  + 컨텍스트 선택
  + 도구 정의
  + 파일·터미널 접근
  + 권한과 샌드박스
  + 상태와 메모리
  + 오류 처리
  + 검증
  + 관측 가능성

Lilian Weng은 하네스를 모델이 어떻게 생각하고 계획하며, 도구를 호출하고, 컨텍스트를 관리하고, 결과를 평가할지 조율하는 모델 주변 시스템으로 설명한다. 또한 하네스는 복잡한 내부 구조를 감추면서 단순한 인터페이스를 제공한다는 점에서 운영체제와 유사하다고 본다.
OpenAI의 Codex 팀이 사용한 표현으로 바꾸면 하네스 엔지니어링은 다음 질문을 다루는 작업이다.
“에이전트가 이 저장소에서 스스로 올바른 일을 할 수 있도록 무엇을 읽을 수 있고, 무엇을 실행할 수 있으며, 어떤 피드백을 받을 수 있게 해야 하는가?”
따라서 하네스 엔지니어링의 주된 제어 대상은 한 번의 에이전트 실행이 작동하는 내부 환경이다.

---
2.2 루프 엔지니어링: 시간과 반복을 설계한다
루프 엔지니어링은 사람이 다음 지시를 계속 입력하는 대신, 시스템이 다음 작업을 발견하고 에이전트를 다시 실행하도록 만드는 것이다.
```
트리거
→ 현재 상태 확인
→ 다음 작업 선택
→ 에이전트 실행
→ 결과 검증
→ 상태 기록
→ 완료·대기·재시도·에스컬레이션 판단
→ 필요하면 반복

루프에는 최소한 다음 요소가 필요하다.
1. 트리거: 언제 시작하는가.
2. 목표: 무엇을 달성해야 하는가.
3. 검증 기준: 달성 여부를 어떻게 확인하는가.
4. 중지 조건: 성공, 실패, 차단, 예산 소진 중 언제 멈추는가.
5. 외부 상태: 다음 실행이 이전 진행 상황을 어떻게 아는가.
Addy Osmani는 실용적인 루프 구성요소로 자동화, 병렬 작업을 위한 워크트리, 지식을 담는 스킬, 외부 도구를 연결하는 플러그인·커넥터, 작성자와 검증자를 분리하는 서브에이전트를 제시한다. 그리고 대화 밖에서 지속되는 파일이나 이슈 보드를 별도의 기억 장치로 추가한다.
루프 엔지니어링에서 중요한 변화는 사람이 사라지는 것이 아니다.
```
기존:
사람이 실행 중간의 모든 다음 행동을 결정

루프 기반:
사람이 목표, 검증, 권한, 중지 조건을 설계
시스템이 반복적인 다음 행동을 결정

즉 사람의 역할이 작업자에서 제어 시스템 설계자와 최종 책임자로 이동한다.

---
2.3 그래프 엔지니어링: 관계와 권한 구조를 설계한다
그래프 엔지니어링은 작업을 노드와 에지, 공유 상태로 표현하는 접근이다.
```
노드:
  결정적 코드
  단일 모델 호출
  도구 실행
  사람 승인
  하나의 완전한 에이전트 루프

에지:
  항상 다음 단계로 이동
  조건에 따라 분기
  실패 시 복구 경로로 이동
  여러 작업을 병렬로 전송
  승인 전까지 대기

상태:
  입력 자료
  작업 결과
  검증 증거
  현재 권한
  오류와 재시도 횟수
  사람의 결정

LangGraph는 이를 State, Nodes, Edges라는 세 요소로 모델링한다. 노드는 일을 수행하고, 에지는 무엇을 다음에 수행할지 결정하며, 공유 상태는 실행 과정에서 변화한다.
LangChain의 설명에서 중요한 점은 노드가 반드시 단순한 LLM 호출일 필요가 없다는 것이다. 노드는 결정적 함수, 도구 호출, 단일 모델 호출 또는 자체 내부 루프를 가진 완전한 에이전트일 수 있다. 그래프의 역할은 모델이 잘할 수 있는 부분에는 자율성을 주고, 순서·권한·규정이 중요한 부분은 코드로 강제하는 것이다.
따라서 그래프 엔지니어링은 여러 작업 단위 사이의 위상과 책임 구조를 설계한다.

3. 세 개념은 어떻게 발전했는가
3.1 1단계: 좋은 질문을 만드는 프롬프트 엔지니어링
초기에는 모델 호출 비용이 비싸고 모델의 지시 이해력이 낮았다. 따라서 역할 부여, 단계별 사고, 출력 포맷, 예시 제공 등의 프롬프트 기법이 큰 영향을 미쳤다.
하지만 에이전트가 파일과 도구를 사용하기 시작하면서 단일 프롬프트만으로 해결할 수 없는 문제가 드러났다.

---
3.2 2단계: 필요한 정보만 넣는 컨텍스트 엔지니어링
컨텍스트 엔지니어링은 모델에게 무엇을 말할지보다 지금 이 단계에서 무엇을 보여줄지에 초점을 둔다.
대규모 저장소 전체를 한 번에 넣는 대신 다음 구조를 사용한다.
```
작은 진입점
→ 관련 문서의 위치
→ 현재 작업과 관련된 파일
→ 필요할 때만 세부 자료 로드

OpenAI의 Codex 팀은 거대한 단일 AGENTS.md가 컨텍스트를 잠식하고, 규칙의 중요도를 희석하며, 빠르게 낡는다는 문제를 경험했다. 대신 짧은 AGENTS.md를 목차처럼 사용하고, 구조화된 docs/와 실행 계획을 저장소 내 기록 시스템으로 삼았다.
컨텍스트 엔지니어링은 하네스 엔지니어링의 핵심 구성요소지만 전체는 아니다. 정보를 잘 보여줘도 도구, 권한, 상태, 검증이 부실하면 에이전트는 실패한다.

---
3.3 3단계: 모델이 일할 수 있는 세계를 만드는 하네스 엔지니어링
하네스 담론을 대중화한 중요한 사례 중 하나는 OpenAI 내부 제품 개발 실험이다.
OpenAI 팀은 사람이 직접 코드를 작성하지 않고 Codex가 애플리케이션 코드, 테스트, CI, 문서, 운영 도구를 작성하도록 했다. 이 과정에서 엔지니어의 주된 업무가 코드 작성에서 다음 업무로 바뀌었다.
```
에이전트가 읽을 수 있는 저장소 만들기
검증 가능한 요구사항 만들기
도구와 피드백 제공하기
아키텍처 불변 조건을 린터로 강제하기
에이전트가 실패한 이유를 환경 개선으로 환류하기

이 팀은 “사람이 조정하고 에이전트가 실행한다”는 원칙, 에이전트 가독성, 저장소 내 지식 체계, 구조적 테스트와 커스텀 린터의 중요성을 강조했다.
이 시기의 핵심 인사이트는 다음과 같다.
모델에게 더 열심히 하라고 요구하기보다, 모델이 성공할 수 있는 환경을 만들어야 한다.

---
3.4 4단계: 사람이 직접 반복하던 일을 시스템화하는 루프 엔지니어링
코딩 에이전트가 여러 시간 동안 일할 수 있게 되면서 새로운 병목이 나타났다.
• 사람이 계속 “계속해”, “테스트해”, “다시 확인해”라고 말해야 한다.
• 에이전트가 한 세션을 끝낼 때마다 다음 작업을 다시 지정해야 한다.
• 여러 에이전트의 진행 상황을 사람이 여러 터미널에서 관리해야 한다.
Boris Cherny의 “내가 하는 일은 이제 프롬프트를 쓰는 것이 아니라 루프를 쓰는 것”이라는 발언과 Peter Steinberger의 “코딩 에이전트에 직접 프롬프트를 넣지 말고, 에이전트에 프롬프트를 넣는 루프를 설계하라”는 주장이 이 변화를 상징했다. Addy Osmani는 이를 자동화, 워크트리, 스킬, 커넥터, 서브에이전트와 외부 메모리라는 구체적 구성으로 정리했다.
하지만 여기에는 중요한 제한이 있다.
• 루프는 부정확한 목표도 빠르게 반복한다.
• 검증이 약하면 오류를 자동 증폭한다.
• 작성자와 검증자가 같으면 자기 결과를 관대하게 평가한다.
• 토큰과 실행 비용이 눈에 띄지 않게 증가한다.
• 사용자가 코드를 이해하지 않으면 이해 부채가 누적된다.
Osmani는 이를 comprehension debt, 즉 자신이 소유한 시스템에 대한 이해가 생산 속도를 따라가지 못하는 문제와 cognitive surrender, 즉 판단을 에이전트에게 사실상 포기하는 문제로 설명한다.
따라서 루프는 “무한히 계속하라”가 아니라 다음과 같아야 한다.
```
명확한 목표
+ 관찰 가능한 진행 상태
+ 기계적 검증
+ 제한된 예산
+ 명시적 중지 상태
+ 사람에게 넘기는 조건


---
3.5 5단계: 여러 루프와 책임을 구조화하는 그래프 엔지니어링
루프가 늘어나면 다시 문제가 생긴다.
```
어느 루프가 먼저 실행되어야 하는가?
어떤 작업은 병렬로 실행해도 되는가?
어떤 에이전트가 어떤 파일을 수정할 수 있는가?
검증 실패 시 어디로 돌아가야 하는가?
어느 단계에서 사람의 승인이 필요한가?
한 작업의 결과를 다른 작업이 어떻게 받아야 하는가?

이때 단일 루프 안에 조건문을 계속 추가하면 숨겨진 상태 머신이 만들어진다.
```
while not done:
    if A:
        ...
    elif B:
        ...
    if retry:
        ...
    if reviewer_failed:
        ...
    if approval_required:
        ...

규모가 작을 때는 괜찮지만, 책임과 실패 경계가 늘어나면 전체 구조를 명시적 그래프로 표현하는 것이 유리하다.
OpenAI의 Symphony는 이슈 트래커를 상태 머신과 제어판으로 사용한다. 각 작업은 독립된 에이전트 작업공간에 대응하고, 선행 작업이 끝난 작업만 실행되며, 에이전트가 중단되면 다시 시작된다. 큰 작업은 의존성을 가진 작업 트리나 DAG로 분해된다.
Microsoft Agent Framework도 단일 에이전트가 실행 순서를 안정적으로 보장할 수 없는 경우에만 워크플로를 도입하라고 권고한다. 명시적 워크플로는 조건 분기, 병렬 처리, 체크포인트, 사람 승인, 재개 가능한 장기 실행을 제공한다.

---
3.6 6단계: 스스로 개선되는 하네스와 그래프
다음 단계는 사람이 하네스를 수동으로 개선하는 것을 넘어, 실행 이력과 평가 결과를 이용해 하네스 자체를 최적화하는 것이다.
Lilian Weng은 최적화 대상의 확대를 다음처럼 설명한다.
```
명령 프롬프트
→ 구조화된 컨텍스트
→ 워크플로
→ 하네스 코드
→ 하네스를 개선하는 최적화 코드

여기서 모델은 단순히 문제의 답을 만드는 것이 아니라 다음을 수정한다.
• 어떤 정보를 저장할지
• 어떤 정보를 검색할지
• 어떤 도구를 노출할지
• 어떤 작업 분해를 사용할지
• 어떤 실패를 재시도할지
• 어떤 스킬을 유지할지
• 어떤 검증을 추가할지
Meta-Harness와 Agentic Harness Engineering 같은 연구는 실행 궤적, 오류 원인, 성능 지표를 바탕으로 하네스 구성요소를 수정하는 방향을 탐구한다.
다만 하네스가 스스로 자신을 수정할 때는 다음 영역이 편집 불가능한 외부 경계로 남아야 한다.
```
최종 평가기
권한 정책
비용 한도
감사 로그
안전 샌드박스
배포 승인
핵심 데이터 보호 규칙

에이전트가 평가기를 비활성화하거나 비용 한도를 올리는 방식으로 “성능을 개선”할 수 있어서는 안 된다.

```
볼 수 있는 정보
사용할 수 있는 도구
접근 가능한 파일
네트워크 권한
메모리
샌드박스
검증기


---
5.2 루프는 시간적 제어다
에이전트가 언제 다시 행동하고 언제 멈추는지를 정한다.

```

합류
승인

따라서 보다 정확한 발전 과정은 다음과 같다.
```

어떻게 반복하게 할 것인가             루프

경험을 통해 무엇을 바꿀 것인가         학습·진화

6. 하네스, 루프, 그래프의 경계가 자주 혼동되는 이유
6.1 모든 하네스에는 이미 내부 에이전트 루프가 있다
Codex, Claude Code, Hermes 모두 기본적으로 다음 구조를 가진다.
```
모델 호출
→ 도구 요청
→ 도구 실행
→ 결과를 모델에 반환
→ 추가 도구 또는 최종 응답

OpenAI는 이를 Codex 에이전트 루프의 핵심 로직으로 설명한다. Hermes의 AIAgent도 프롬프트 구성, 모델 호출, 도구 실행, 결과 삽입과 재호출을 반복한다.
그러나 루프 엔지니어링에서 말하는 루프는 보통 이 내부 도구 호출 루프보다 한 단계 위다.
```
내부 루프:
모델 ↔ 도구

외부 루프:
작업 발견 ↔ 에이전트 실행 ↔ 검증 ↔ 다음 작업


---
6.2 하나의 루프도 내부적으로 작은 그래프다
계획, 실행, 검증, 재시도는 상태와 분기를 가진다. 따라서 구현 관점에서는 루프도 그래프로 표현할 수 있다.
반대로 그래프의 한 노드 안에서 하나의 에이전트 루프가 몇 시간 동안 실행될 수도 있다.
그래서 다음 주장은 모두 맞다.
• 하네스는 루프를 포함한다.
• 루프는 그래프로 표현할 수 있다.
• 그래프 노드는 하네스를 가진 에이전트 루프일 수 있다.
• 하네스 내부의 워크플로도 그래프일 수 있다.
용어보다 중요한 것은 어느 레이어를 지금 설계하고 있는가를 명확히 하는 것이다.

---
7. 모델 지능과 하네스의 관계
7.1 모델과 에이전트는 같은 것이 아니다
에이전트는 다음처럼 이해해야 한다.
```
에이전트
= 모델
+ 하네스
+ 도구
+ 실행 환경
+ 상태
+ 운영 정책

같은 모델을 사용하더라도 다음 차이로 결과가 크게 달라질 수 있다.
• 도구 설명의 정확성
• 패치 적용 방식
• 터미널 출력의 전달 방식
• 컨텍스트 압축 정책
• 계획과 할 일 관리
• 파일 탐색 기능
• 권한 승인 방식
• 검증 명령
• 재시도 정책
• 서브에이전트 격리
• 작업 완료 판단
반대로 같은 하네스에 서로 다른 모델을 연결하면 계획 능력, 도구 선택, 장기 지시 준수, 오류 복구 능력이 달라진다.

---
7.2 강한 모델일수록 하네스가 단순해질 수 있다
강한 모델은 다음 능력이 상대적으로 우수하다.
• 모호한 요구사항 해석
• 저장소 구조 탐색
• 긴 작업의 계획 유지
• 적절한 도구 선택
• 명령 결과에서 오류 원인 추론
• 중간 계획 수정
• 여러 제약의 동시 준수
• 어느 시점에 질문해야 하는지 판단
따라서 모델이 강해질수록 세세한 규칙과 고정된 분기를 줄이고 더 일반적인 원칙을 줄 수 있다.
Anthropic은 하네스가 “모델이 스스로 못할 것”이라는 가정을 코드로 고정하는데, 모델이 개선되면 그러한 가정이 낡을 수 있다고 지적한다. 그래서 모델의 두뇌와 실제 작업을 수행하는 샌드박스·도구를 안정된 인터페이스로 분리하려 한다.
강한 모델에 낡은 보조 규칙이 너무 많으면 다음 문제가 생긴다.
```
불필요한 계획 반복
과도한 확인 질문
이미 가능한 작업을 강제로 분해
잘못된 휴리스틱으로 도구 선택 제한
컨텍스트를 낡은 규칙이 차지
모델의 더 나은 판단을 그래프가 차단


---
7.3 중간 수준 모델은 하네스의 효과를 가장 크게 볼 수 있다
중간 수준 모델은 문제를 해결할 기본 지능은 있지만 장기 작업에서 일관성이 떨어질 수 있다. 이 경우 다음 요소가 큰 효과를 낸다.
• 명시적인 할 일 목록
• 좁은 도구 세트
• 작업별 스킬
• 단계별 증거 기록
• 독립 검증
• 짧은 반복 주기
• 파일 기반 상태
• 실패 원인 분류
• 구조화된 완료 계약
Agentic Harness Engineering 연구에서는 시스템 프롬프트만 바꾸기보다 도구, 미들웨어, 장기 메모리 같은 하네스 구조를 개선했을 때 여러 모델 계열에서 성능 개선이 전이되는 결과를 보고했다. 다만 이는 제한된 벤치마크 환경의 결과이므로 모든 실무에 동일하게 일반화된다고 보아서는 안 된다.

---
7.4 약한 모델에는 복잡한 그래프보다 작은 문제와 강한 검증이 낫다
약한 모델에 많은 도구와 서브에이전트를 제공하면 능력이 합산되기보다 오류 표면이 커질 수 있다.
```
도구 수 증가
→ 선택 오류 증가

컨텍스트 증가
→ 핵심 지시 희석

서브에이전트 증가
→ 잘못된 결과의 합성 위험 증가

루프 길이 증가
→ 초반 오류 누적

동적 분기 증가
→ 상태 추적 실패

약한 모델에는 다음 구성이 적절하다.
```
한 번에 하나의 명확한 작업
작은 파일 범위
제한된 도구
결정적 실행 순서
기계적 테스트
짧은 반복
낮은 최대 턴 수
사람의 잦은 체크포인트

“약한 모델을 여러 개 연결하면 강한 에이전트가 된다”는 주장은 검증 없이 받아들이기 어렵다. 모델 간 토론과 다수결도 모든 에이전트가 같은 오해를 공유하면 오류를 강화할 수 있다.

8. Codex, Claude Code, Hermes의 구조적 차이
8.1 Codex
기본 성격
Codex는 OpenAI의 코딩 모델과 긴밀하게 공동 설계된 코딩 에이전트 제품군이다. CLI, IDE, ChatGPT, 클라우드 실행 환경을 연결하고, 워크트리와 클라우드 환경을 통한 병렬 작업, 스킬, 백그라운드 자동화 기능을 제공한다.
강점
1. 모델–하네스 공동 최적화
모델 프로토콜, 추론 방식, 도구 표현, 샌드박스, 컨텍스트 구성 방식이 같은 공급자 안에서 최적화된다. 범용 OpenAI 호환 API 위에 얹은 하네스보다 모델 특성을 적극 활용하기 쉽다.
2. 저장소 중심의 코딩 작업
AGENTS.md, 저장소 내 문서, 실행 계획, 테스트와 린터를 중심으로 장기 개발 작업을 수행하는 데 강하다.
3. 병렬 에이전트 작업
워크트리와 클라우드 환경을 통해 여러 에이전트가 서로 다른 작업을 병렬로 수행하기 쉽다.
4. 하네스에서 오케스트레이션으로의 자연스러운 확장
Symphony처럼 이슈 트래커를 제어판으로 사용해 여러 Codex 실행을 지속적으로 조율하는 구조가 공개되고 있다.
5. 안전 경계의 제품화
샌드박스, 네트워크 접근, 승인 정책이 제품 수준에서 통합되어 있다.
약점과 유의점
• OpenAI 모델과 제품 생태계에 최적화되어 있어 공급자 교체 자유도가 낮다.
• 소프트웨어 엔지니어링 외의 지속형 개인 에이전트 용도에서는 별도 구조가 필요할 수 있다.
• 모델과 제품 업데이트가 빠르므로 자체 스킬과 운영 규칙을 계속 검증해야 한다.
• 클라우드·병렬 에이전트 사용이 늘어나면 사용량과 검토 병목도 함께 증가한다.
• Codex의 좋은 성과를 다른 모델에 동일한 프롬프트만 적용해 재현하기 어렵다.
적합한 사용자
```
전문 소프트웨어 개발자
대형 저장소를 운영하는 팀
PR·CI·리뷰 자동화를 원하는 조직
OpenAI 생태계를 주력으로 사용하는 사용자
에이전트 친화적인 저장소를 만들 의지가 있는 팀


---
8.2 Claude Code
기본 성격
Claude Code는 Claude 모델을 터미널과 코드 저장소에 결합한 에이전트다. Unix 도구와의 조합, MCP 연결, 훅, 서브에이전트, 권한 제어, 장기 작업 하네스와 Agent SDK를 주요 축으로 한다.
강점
1. 강한 장기 추론과 코드 이해
복잡한 저장소 분석, 리팩터링, 설계 설명, 긴 작업에 적합하다.
2. 터미널 중심의 높은 조합 가능성
쉘 파이프라인, 비대화형 실행, GitHub Actions, 훅과 외부 스크립트를 조합해 자체 루프를 만들기 쉽다.
3. 장기 실행을 위한 실전 하네스 패턴
Anthropic은 초기 환경을 구성하는 initializer agent와 이후 점진적으로 작업하는 coding agent를 분리하고, 기능 목록·진행 파일·Git 이력을 통해 컨텍스트 윈도 사이의 상태를 이어가는 방법을 제시했다.
4. 서브에이전트와 병렬 팀
역할별 에이전트와 병렬 실행을 쉽게 실험할 수 있다.
5. MCP와 Agent SDK
Claude Code에서 검증된 하네스 기능을 다른 업무 에이전트로 확장할 수 있다.
약점과 유의점
• Claude 모델 계열에 의존한다.
• 모델 버전이 바뀌면 기존 하네스의 가정이 빠르게 낡을 수 있다.
• 장기 루프와 다중 에이전트는 토큰 사용량이 매우 커질 수 있다.
• dangerously-skip-permissions와 같은 완전 자율 모드는 반드시 격리 환경에서 사용해야 한다.
• 높은 추론 능력 때문에 결과가 설득력 있어 보여도 실제 검증을 생략해서는 안 된다.
• 장시간 병렬 작업은 작성량보다 검토와 통합 능력이 병목이 된다.
Anthropic의 병렬 에이전트 실험에서도 단순 루프와 다수 에이전트가 큰 작업을 수행할 수 있었지만, 테스트 설계, 작업 분할, 공유 저장소 충돌, 비용, 작업 한계가 주요 문제로 나타났다.
적합한 사용자
```
터미널 중심의 숙련 개발자
복잡한 분석과 설계를 자주 수행하는 사용자
MCP와 쉘 스크립트를 적극 활용하는 팀
Claude 모델을 주력으로 사용하는 조직
자체 루프와 자동화를 세밀하게 구성하려는 사용자

8.3 Hermes Agent
기본 성격
Hermes Agent는 Nous Research가 개발한 오픈소스·멀티모델 에이전트 하네스다. CLI뿐 아니라 메시징 게이트웨이, 스케줄러, API, IDE 연동, 메모리, 스킬, 프로필, 서브에이전트와 여러 실행 백엔드를 제공한다. 공식 아키텍처상 하나의 AIAgent 코어가 프롬프트 구성, 공급자 선택, 도구 실행, 재시도, 폴백, 컨텍스트 압축과 지속성을 담당한다.
강점
1. 모델 독립성
OpenAI, Anthropic, OpenRouter, 로컬·자체 호환 엔드포인트 등 여러 공급자를 사용할 수 있다. 모델과 공급자를 비용, 속도, 품질 기준으로 선택하거나 폴백할 수 있다.
2. 지속형 개인 에이전트
CLI 세션에 국한되지 않고 Telegram, Discord, Slack 등 여러 표면에서 같은 에이전트와 메모리를 사용할 수 있다.
3. 절차적 메모리인 스킬
스킬은 필요할 때만 로드되는 지식·절차 문서이며, 에이전트가 새 스킬을 만들거나 기존 스킬을 개선할 수 있다. 프로그레시브 디스클로저를 사용해 모든 지식을 매번 컨텍스트에 넣지 않는다.
4. 장기 기억과 세션 검색
파일 기반 메모리와 세션 저장소, 선택적 외부 메모리 공급자를 사용할 수 있다. 스킬·메모리 쓰기에 승인 단계를 설정할 수도 있다.
5. 프로필과 격리
코딩, 연구, 개인 비서와 같이 목적별 프로필을 분리해 설정, 메모리, 세션, 게이트웨이를 격리할 수 있다.
6. 다양한 샌드박스 백엔드
로컬, Docker, SSH, Modal, Singularity 등 환경에 맞는 실행 계층을 사용할 수 있다.
7. 내장된 목표 루프
/goal은 지속 목표, 별도 판정 모델, 턴 예산, 대기와 재개, 완료 계약을 지원한다. 완료 계약에는 결과, 검증, 보존 제약, 작업 범위, 중지 조건을 명시할 수 있다.
약점과 유의점
1. 품질의 모델 의존성이 크다
하네스가 동일해도 연결한 모델의 도구 선택, 장기 계획, 한국어 이해, 코딩 능력에 따라 결과가 크게 달라진다.
2. 넓은 기능 표면
도구, 공급자, 메모리, 스킬, 게이트웨이, 샌드박스가 많아 잘못 구성하면 단순한 코딩 에이전트보다 운영 복잡성이 높아진다.
3. 모델–하네스 공동 설계가 약하다
특정 모델에 깊이 최적화된 Codex나 Claude Code와 달리, 여러 API 형식을 공통 내부 표현으로 수렴시킨다. 유연성은 높지만 각 모델의 특수 기능을 완전히 활용하려면 추가 튜닝이 필요하다.
4. 작은 모델에서 도구 혼동 가능성
도구가 많을수록 약한 모델은 비슷한 도구를 혼동하거나 터미널을 만능 도구처럼 사용할 수 있다. 프로필별 도구 축소와 명시적 스킬이 중요하다.
5. 자기 수정에 대한 거버넌스 필요
에이전트가 스킬과 메모리를 갱신하는 능력은 장점이지만, 잘못된 절차나 일시적 해결책을 장기 지식으로 저장할 수 있다. 중요한 프로필에서는 스킬 쓰기 승인과 변경 이력이 필요하다.
적합한 사용자
```
여러 모델을 비교·교체하려는 사용자
로컬 모델과 클라우드 모델을 함께 사용하는 사용자
개인 에이전트를 장기 운영하려는 사용자
메신저·스케줄러·자동화를 통합하려는 사용자
하네스를 직접 수정하고 확장하려는 개발자
모델·데이터·인프라 통제권을 중시하는 사용자

10. 언제 직접 프롬프트를 쓰고, 언제 루프나 그래프를 사용해야 하는가
10.1 직접 프롬프트가 적합한 경우
• 일회성 질문
• 탐색적 대화
• 요구사항이 아직 형성되지 않은 작업
• 사람의 취향과 판단이 매 단계 필요한 작업
• 짧은 수정
• 검증 기준을 아직 정의할 수 없는 작업
```
예:
“이 설계의 가장 큰 위험을 세 가지 관점에서 검토해줘.”

이 단계에서 루프를 만들면 아직 정의되지 않은 목표를 자동 반복하게 된다.

---
10.2 단일 에이전트 하네스가 적합한 경우
• 하나의 저장소나 작업공간에서 끝나는 작업
• 한 에이전트가 전체 컨텍스트를 이해할 수 있는 작업
• 도구 호출과 몇 차례의 수정으로 해결되는 작업
• 사람이 결과를 바로 검토할 수 있는 작업
```
예:
“이 버그를 재현하고 최소 수정으로 고친 뒤 관련 테스트를 실행해.”


---
10.3 루프가 적합한 경우
• 같은 목표를 여러 번 시도해야 한다.
• 에이전트가 한 번의 응답 후 너무 일찍 멈춘다.
• 테스트나 외부 신호를 기다려야 한다.
• 다음 작업을 반복적으로 발견할 수 있다.
• 진행 상태를 외부 파일이나 이슈에 남길 수 있다.
• 완료 여부를 비교적 객관적으로 검증할 수 있다.
```
예:
“CI가 통과할 때까지 실패 원인을 고치되, DB 변경이 필요하면 중지해.”


---
10.4 그래프가 적합한 경우
• 작업 순서를 반드시 보장해야 한다.
• 병렬 실행과 합류가 필요하다.
• 서로 다른 권한을 가진 작업자가 있다.
• 사람 승인 단계가 있다.
• 실패 유형별 복구 경로가 다르다.
• 여러 시스템 사이에서 상태를 전달해야 한다.
• 작업 중 일부는 결정적 코드로 처리해야 한다.
• 각 단계의 감사 기록이 필요하다.
```
예:
요구 분석
→ 보안 검토
→ 구현과 테스트 작성 병렬 수행
→ 통합 테스트
→ 배포 승인
→ 점진 배포
→ 메트릭 검증
→ 전체 배포 또는 롤백

11. 다양한 사용자에게 권장하는 방향
11.1 일반 코딩 에이전트 사용자
처음부터 루프나 그래프를 만들 필요는 없다.
권장 순서:
```
1. 하나의 강한 에이전트 사용
2. 프로젝트 지침을 짧고 명확하게 작성
3. 테스트·린트·빌드 명령을 알려줌
4. 작업 전 계획과 작업 후 검증을 요구
5. 반복되는 절차만 스킬로 저장

이 단계에서 가장 큰 효과를 내는 것은 멀티에이전트가 아니라 검증 가능한 저장소다.

---
11.2 파워 유저와 1인 개발자
다음 단계로 작은 루프를 도입할 수 있다.
```
이슈 조사 루프
테스트 실패 수정 루프
의존성 업데이트 루프
문서 정리 루프
일일 저장소 상태 점검

단, 자동 병합보다 “검토 가능한 PR 생성”을 기본 종료 상태로 두는 것이 안전하다.
추천 구조:
```
발견
→ 변경
→ 테스트
→ 독립 리뷰
→ PR 생성
→ 사람 승인


---
11.3 개발 팀과 기술 리더
개별 에이전트 사용법보다 저장소와 조직 프로세스를 정비해야 한다.
우선순위는 다음과 같다.
```
1. 저장소 내 지식 체계
2. 실행 가능한 요구사항과 계획
3. 빠르고 결정적인 테스트
4. 아키텍처 규칙의 린터화
5. 관측 가능한 에이전트 실행
6. 에이전트별 격리 작업공간
7. PR과 이슈 상태를 이용한 오케스트레이션

에이전트가 늘어날수록 코드 작성보다 리뷰, 제품 판단, 우선순위 결정이 병목이 된다. 따라서 처리량만 높이는 것보다 사람의 검토 대역폭을 보호해야 한다.

---
11.4 로컬·오픈 모델 사용자
로컬 모델은 비용 통제와 데이터 주권 측면에서 유리하지만, 도구 선택과 장기 작업 일관성이 프런티어 모델보다 약할 수 있다.
권장 방식:
```
프로필별 도구 수 축소
업무별 스킬 명시
작은 작업 단위
파일 기반 계획과 상태
짧은 목표 루프
기계적 검증
고난도 설계·리뷰만 상위 모델에 위임

효율적인 혼합 구성은 다음과 같다.
```
로컬 모델:
  검색, 정리, 반복 수정, 로그 분석, 단순 구현

강한 클라우드 모델:
  아키텍처 판단, 난해한 오류, 최종 리뷰, 목표 재설계

모든 작업을 한 모델에 맡기는 것보다 역할별 모델 포트폴리오를 구성하는 편이 비용과 품질을 함께 개선할 수 있다.

---
11.5 Hermes 같은 지속형 개인 에이전트 사용자
개인 에이전트는 코딩 에이전트보다 기억과 프라이버시 경계가 더 중요하다.
권장 구조:
```
개인 프로필
업무 프로필
코딩 프로필
공용 채널 프로필

각 프로필은 다음을 분리해야 한다.
• 메모리
• 도구
• 접근 권한
• 메시징 채널
• 스킬
• 모델
• 기록 보존 정책
지속 기억은 많이 저장하는 것보다 무엇을 저장하지 않을지가 중요하다. 자동 생성 스킬과 메모리는 승인 또는 정기적인 정리 절차를 두는 편이 좋다.

---
11.6 에이전트 플랫폼 개발자
에이전트 플랫폼은 하나의 거대한 그래프보다 다음 세 레이어를 분리하는 것이 좋다.
```
1. Agent Runtime
   모델, 도구, 컨텍스트, 권한, 세션

2. Loop Controller
   목표, 예산, 검증, 대기, 재시도

3. Workflow Orchestrator
   작업 의존성, 병렬 실행, 승인, 복구

이 분리의 장점은 다음과 같다.
• 모델을 바꿔도 전체 그래프를 다시 만들 필요가 없다.
• 하네스의 내부 구현을 바꿔도 업무 상태는 유지된다.
• 하나의 에이전트 실행이 실패해도 전체 작업은 복구된다.
• 그래프 엔진을 도입하지 않아도 작은 루프부터 시작할 수 있다.
• 관측과 비용을 레이어별로 측정할 수 있다.

---
12. 실무 설계 원칙
원칙 1. 가장 작은 구조에서 시작한다
```
함수로 해결 가능 → 함수
단일 모델 호출로 가능 → 모델 호출
단일 에이전트로 가능 → 에이전트
반복이 필요 → 루프
책임과 의존성이 분리됨 → 그래프

Microsoft 역시 함수로 처리할 수 있는 작업에 에이전트를 사용하지 말고, 단일 에이전트로 가능한 작업에 워크플로를 서둘러 도입하지 말 것을 권한다.

---
원칙 2. 목표보다 완료 계약을 작성한다
나쁜 목표:
```
인증 시스템을 개선해.

좋은 완료 계약:
```
결과:
세션 쿠키 인증을 JWT 방식으로 전환한다.

검증:
인증 테스트 전체 통과
로그인·갱신·로그아웃 시나리오 통과
기존 응답 스키마 회귀 없음

제약:
DB 스키마는 변경하지 않는다.
공개 API 응답 형식을 유지한다.

범위:
services/auth 및 관련 테스트만 수정한다.

중지:
DB 마이그레이션 또는 외부 서비스 변경이 필요하면 사람에게 보고한다.

Hermes의 /goal 완료 계약도 결과, 검증, 제약, 범위, 중지 조건을 명시하도록 설계되어 있다.

---
원칙 3. 작성자와 검증자를 분리한다
최소한 다음 중 하나를 사용한다.
```
작성 에이전트 ≠ 리뷰 에이전트
작성 모델 ≠ 판정 모델
생성 프롬프트 ≠ 검증 프롬프트
코드 작성 ≠ 기계적 테스트

그러나 별도 리뷰 에이전트도 증거 없이 “좋아 보인다”고 말할 수 있다. 따라서 리뷰 모델보다 테스트, 타입 검사, 실행 결과, 외부 시스템 상태를 우선해야 한다.

---
원칙 4. 완료는 발언이 아니라 상태 전이다
에이전트의 다음 문장은 완료 증거가 아니다.
```
“작업을 성공적으로 완료했습니다.”

완료는 그래프에서 다음 전이가 허용됐다는 의미여야 한다.
```
IMPLEMENTED
  └─ 테스트 증거 있음
       → VERIFIED

VERIFIED
  └─ 승인 있음
       → READY_TO_MERGE

즉 에이전트 출력은 주장이며, 테스트와 승인 결과가 상태다.

---
원칙 5. 상태를 대화 밖에 둔다
장기 작업의 상태를 모델 대화에만 보관하면 다음 세션에서 유실되거나 압축 과정에서 왜곡된다.
적합한 상태 저장소:
```
Git
작업 계획 파일
JSON 상태 파일
이슈 트래커
체크포인트 DB
테스트 리포트
구조화 로그

Lilian Weng과 Anthropic 모두 파일과 Git 이력을 장기 에이전트의 중요한 지속 상태로 강조한다.

---
원칙 6. 에이전트가 아닌 실패 경계를 분리한다
서브에이전트를 만드는 기준은 “역할 이름을 붙일 수 있는가”가 아니다.
다음 중 하나가 다를 때 분리한다.
```
권한
컨텍스트
모델
비용 등급
실패 영향
검증 방법
작업 공간
수명 주기

예를 들어 구현자와 보안 검토자는 권한과 성공 기준이 다르므로 분리할 가치가 있다.
반면 “아이디어 에이전트”, “창의성 에이전트”, “천재 리뷰어 에이전트”처럼 프롬프트 역할만 다르고 상태·권한·검증이 같다면 실질적 분리가 아닐 수 있다.

---
원칙 7. 결정적 코드와 모델 판단을 혼합한다
좋은 그래프는 모든 노드에 LLM을 넣지 않는다.
```
정규식으로 가능한 분류      → 코드
스키마 검증                 → 코드
권한 검사                   → 코드
모호한 의도 해석            → 모델
새로운 해결 전략 수립       → 모델
코드 작성                   → 코딩 에이전트
배포 승인                   → 사람 또는 정책

그래프의 가치는 에이전트를 많이 사용하는 데 있지 않고, 모델이 필요한 위치에만 모델을 배치하는 것에 있다.

---
원칙 8. 루프에는 예산이 있어야 한다
각 루프는 다음 한도를 가져야 한다.
```
최대 턴 수
최대 실행 시간
최대 토큰 또는 비용
최대 동시 에이전트
최대 재시도
최대 변경 파일

한도 소진은 실패가 아니라 정상적인 종료 상태다.
```
SUCCESS
BLOCKED
BUDGET_EXHAUSTED
NEEDS_HUMAN
NO_PROGRESS
CANCELLED


---
원칙 9. 모델 업그레이드 시 하네스를 다시 단순화한다
새 모델을 도입할 때 기존 규칙을 그대로 두고 성능만 비교해서는 안 된다.
점검 대상:
• 이제 필요 없는 강제 계획 단계가 있는가.
• 모델이 직접 할 수 있는 일을 서브에이전트로 우회하는가.
• 낡은 프롬프트 트릭이 남아 있는가.
• 컨텍스트 압축 임계값이 적절한가.
• 도구 설명이 새 모델의 사용 방식과 맞는가.
• 기존 검증자는 새 모델의 오류를 잡을 수 있는가.
모델이 발전하면 하네스가 사라지는 것이 아니라, 하네스의 불필요한 부분을 제거하는 작업이 필요하다.

---
13. 자주 발생하는 안티패턴
13.1 거대한 지침 파일
모든 규칙을 하나의 AGENTS.md, CLAUDE.md, SYSTEM.md에 넣는다.
결과:
```
컨텍스트 낭비
우선순위 소실
낡은 규칙 누적
상충 규칙
검증 불가능

대안은 짧은 지도와 구조화된 세부 문서다.

---
13.2 검증 없는 무한 루프
```
while true:
    agent("계속 개선해")

완료의 정의가 없으므로 비용을 소비하거나 불필요한 변경을 계속한다.

---
13.3 자기 리뷰만 반복
같은 에이전트에게 구현 후 “스스로 다시 검토해”라고 한다.
자기 검토는 유용하지만 독립 검증을 대체하지 못한다.

---
13.4 모든 문제를 멀티에이전트로 해결
에이전트가 많아지면 다음 비용도 증가한다.
```
컨텍스트 복제
결과 합성
상충 해결
토큰 사용
상태 관리
추적 난이도

전문화가 실제 권한·도구·검증 차이로 연결되지 않으면 멀티에이전트는 역할극에 가까워질 수 있다.

---
13.5 그래프를 너무 일찍 고정
초기 탐색 단계에서 전체 업무를 고정 그래프로 만들면 실제 문제를 배우기 전에 잘못된 프로세스를 코드로 굳힌다.
권장 방식:
```
사람과 단일 에이전트로 탐색
→ 반복되는 패턴 관찰
→ 작은 루프로 자동화
→ 안정된 경계만 그래프로 승격


---
13.6 모델 차이를 무시한 공통 하네스
모든 모델에 같은 도구, 같은 프롬프트, 같은 턴 예산을 적용한다.
모델마다 다음 특성이 다르다.
• 병렬 도구 호출 능력
• 시스템 지시 우선순위
• 컨텍스트 압축 내성
• 질문 성향
• 완료를 선언하는 성향
• 도구 오류 후 복구 능력
• 장기 목표 유지
하네스는 공통 인터페이스를 제공하되 모델별 프로필을 허용해야 한다.

---
13.7 관측 데이터는 많지만 개선하지 않음
모든 실행을 추적하더라도 아무도 대량의 트레이스를 읽지 않으면 가치가 없다.
관측 가능성은 로그 수집이 아니라 다음 질문에 답할 수 있어야 한다.
```
어디에서 실패했는가?
왜 실패했는가?
모델, 도구, 컨텍스트, 그래프 중 무엇의 책임인가?
같은 실패가 얼마나 반복되는가?
어떤 변경 후 개선됐는가?
비용 증가가 품질 증가로 이어졌는가?

LangChain도 대규모 트레이스를 단순히 저장하는 것과 행동 패턴을 분석해 개선하는 것은 별개라고 지적한다.

---
14. 권장 성숙도 로드맵
단계 0. 보조 도구
```
사람이 모든 작업을 수행
모델은 설명과 초안을 제공

목표: 모델의 장단점 파악.

---
단계 1. 단일 에이전트
```

15. 최종 방향성
15.1 하네스 엔지니어링은 기본 인프라가 된다
모델이 아무리 좋아져도 다음 외부 세계는 남는다.
• 파일과 데이터
• 권한
• 도구
• 네트워크
• 메모리
• 안전 경계
• 검증
• 사람과 조직
따라서 하네스는 사라지지 않는다. 다만 모델이 발전할수록 모델의 부족함을 보완하는 임시 규칙은 줄고, 안정된 인터페이스와 운영 경계의 중요성이 커질 것이다.

---
15.2 루프 엔지니어링은 자동화의 실질적 단위가 된다
앞으로 사용자는 프롬프트 템플릿보다 다음과 같은 작업 계약을 더 많이 만들게 될 가능성이 높다.
```
언제 시작한다.
무엇을 목표로 한다.
어떤 증거가 필요하다.
어떤 범위를 건드릴 수 있다.
언제 사람에게 넘긴다.
어느 정도 비용까지 허용한다.

이는 프롬프트 엔지니어링의 종말이 아니다. 프롬프트가 루프 내부의 구성요소로 내려가는 것이다.

---
15.3 그래프 엔지니어링은 프로덕션 시스템에서 중요해진다
개인 사용에서는 하나의 강한 에이전트와 작은 루프로 충분한 경우가 많다.
그러나 기업과 고위험 업무에서는 다음 요구가 발생한다.
• 감사 가능한 상태
• 책임 분리
• 권한 격리
• 사람 승인
• 장애 복구
• 장기 실행
• 비용과 동시성 관리
• 여러 시스템 통합
이때 그래프는 에이전트의 창의성을 줄이는 족쇄가 아니라, 창의적 판단을 허용할 수 있는 안전한 경계를 만든다.

---
15.4 가장 좋은 시스템은 완전 자율이 아니라 선택적 자율이다
좋은 에이전트 시스템은 모든 것을 모델에게 결정하게 하지 않는다.
```
명확한 규칙은 코드가 결정한다.
모호한 문제는 모델이 판단한다.
고위험 상태 전이는 사람이 승인한다.
성공 여부는 증거가 결정한다.

그래프 엔지니어링의 핵심은 에이전트 수가 아니라 이 경계를 올바르게 배치하는 것이다.

---
16. 결론
하네스 엔지니어링, 루프 엔지니어링, 그래프 엔지니어링의 발전은 “더 멋진 용어”로의 이동이 아니다.
이는 AI 사용의 중심이 다음처럼 바뀌는 과정이다.
```
좋은 답을 받는다
→ 에이전트가 일을 하게 한다
→ 에이전트가 계속 일하게 한다
→ 여러 에이전트와 시스템이 함께 일하게 한다
→ 그 시스템이 경험을 통해 개선되게 한다

그러나 추상화 레이어가 높아질수록 사람의 책임이 줄어드는 것은 아니다. 오히려 책임의 성격이 바뀐다.
```
과거의 책임:
코드를 직접 올바르게 작성한다.

현재의 책임:
올바른 코드가 생성되고 검증되고 승인되는 시스템을 만든다.

Codex는 모델과 하네스를 강하게 통합해 소프트웨어 개발의 높은 생산성을 추구한다. Claude Code는 강한 추론 능력과 터미널 조합성을 기반으로 사용자가 직접 루프와 에이전트 팀을 구성하기 좋다. Hermes는 모델 독립성, 지속 기억, 스킬, 메시징과 자동화를 결합해 장기 운영 가능한 개방형 에이전트 환경을 제공한다.
어떤 에이전트가 절대적으로 우수한가보다 중요한 질문은 다음과 같다.
```
이 모델은 이 작업을 이해할 수 있는가?
이 하네스는 모델이 성공할 환경을 제공하는가?
이 목표는 검증 가능한가?
반복이 실제로 필요한가?
그래프가 해결할 책임 경계가 존재하는가?
실패했을 때 안전하게 멈추고 복구할 수 있는가?
사용자는 결과를 이해하고 책임질 수 있는가?

이 질문에 답할 수 있다면 새로운 유행어를 따라가는 대신, 자신의 작업에 필요한 만큼만 자율성을 도입할 수 있다.
가장 현실적인 방향은 다음 한 문장으로 요약된다.
강한 단일 에이전트와 단순한 하네스에서 시작하고, 반복이 확인되면 루프를 추가하며, 책임·권한·실패 경계가 실제로 분리될 때만 그래프로 확장하라.
